# etl-utils

> **第一次用 / 隔了很久回来？先看 [START-HERE.md](START-HERE.md)** —— 它只回答一个问题：你现在该干什么。
> 想先弄懂这是什么、以及它背后的想法，再往下读。

> **把"客户给的一堆导出"变成"能入库、能对账、别人敢拿去作决定的结论"——一套可以直接交给 AI 执行的 ETL 工作手册。**
>
> 十步流程 · 11 条可复制指令 · 4 件通用工具 · 附「生成定制版手册」的话术与进度台账

写这套东西的起因很具体：让 AI 写 ETL 代码，它半小时代码就写完了，但你**验证不了对不对**——它说"缺失值已处理"，你只能信。这个仓库解决的就是这一段：**把"怎么验收"写进流程，而不是事后补**。

---

## 先说理念：ETL 不是"把脏数据洗干净"

大部分 ETL 教程教你写代码：读进来、去空值、去重、写出去。这套流程的出发点不一样——**ETL 的难点不在"处理"，在"凭什么这么处理"**。

下面六条是这套东西的底层信念。**每一条都对应一次真实的返工**，不是道德要求。

### 看：动手之前先搞清状况

**① 先看清，再动手。**
反例：拿到表就写清理脚本，见空值就填、见重复就删。三天后发现那批"重复"其实是同一客户的两笔真实成交，删掉的是真生意。
所以流程里**剖析（第 1 步）永远在规则（第 3 步）之前**，而且剖析只描述、不判断——它不预设"什么算异常"。

**② 每条规则都要有依据。**
规则不是"我觉得该去首尾空格"，而是"依据 F04：3,412 行有首尾空格；依据字典第 12 行：该字段应为纯数字"。
没有依据的规则，三个月后**没人敢改，也没人敢删**——它变成了一个没人理解但谁也不敢碰的东西。

### 洗：改得动，也回得去

**③ 原始数据只读，处理结果另存。**
反例：就地覆盖。改错一次就回不去；客户说"你这数和我系统对不上"，你连原件都拿不出来对比。
所以 `data/raw/` 设只读、每轮一个新批次目录、**重跑开新目录不覆盖旧目录**。

**④ 行数对，不等于值对。**
真实踩过：某列映射写错、整列变成空值。四条行数判据全过、灯表全绿——直到算指标那天才发现那列根本没有数据。
所以除了比行数，还要按**确认过的字段映射**比非空率，并检查必填约定。原本就空的可空列不算丢值；阈值须由项目确定，不能按列位置硬比。

### 说：让结论能站住

**⑤ 缺口写在数旁边，不写在附注里。**
反例：报告末尾一句"本数据可能不完整"。客户不会看到，看到了也不知道这影响哪个数。
所以覆盖说明要写清**哪个时间窗、缺了哪一类、影响哪几个指标**，跟指标一起交付。

**⑥ 不知道的不估算。**
反例：上游还有一笔消费没导出 → "按客单价推算约 320 万"。这个数一旦进了 PPT，就再也收不回来了。
所以来源缺口**只描述、不推算**；任何总量结论都必须限定在"已导出范围内"。

## 它解决三个具体问题

| 问题 | 这套东西怎么处理 |
| --- | --- |
| AI 交回来的东西没法验 | 每条指令末尾强制"数／位／法"：条数、文件行号或可重跑的查询、一行能复算的公式。指不出来的，等于没做 |
| 换个客户，之前的方法用不上 | 通用手册管"怎么做"，另有一份话术让 AI 按新业务生成"定制版"，只写这一单的实值与坑 |
| 做到一半忘了自己在哪 | 十行进度台账：状态四态（⬜🟡✅⛔）＋ 每步可勾选的过关判据；另外 `check.py --status` 一条命令就能报进度 |

## 第一次用：头一小时怎么过

### 前 10 分钟：把它挂到项目上

```sh
# 1) 在你的项目目录里拉一份
cd /path/to/your-project
git clone https://github.com/as569951728/etl-utils.git .etl-utils

# 2) 项目根的 AGENTS.md（没有就新建）加一行
#    ETL 工具包在 .etl-utils/，按它的 AGENTS.md 执行；出定制手册前先读 03。

# 3) 把客户给的东西原样放进 materials/，别改名、别转换
```

第 2 步是唯一"必须做对"的事：有了这一行，AI 每次开新会话都会自己读这套规则，**你不用再交代文件在哪**。

### 接下来 30 分钟：先出"四格"，不出手册

对 AI 说一句：

```
读 .etl-utils，给这个客户出一份 ETL 手册
```

它会先给你 **四格背景**——客户与目标／数据清单／已发现问题／已问过谁，每条带出处。**这时候还没有手册，正常。**

你花 5 分钟做三件事：
1. 没出处的条目，**删掉**；
2. 写着"材料中未见"的，你能补就补；
3. 它列的"待我确认"清单，答不了的**留着**——那就是后面访谈要问的东西。

改完回一句"按四格生成手册"，才会拿到那份 250–450 行的定制版。

> 为什么非要单独走这一轮：**四格错了，整份手册全错**。让错误暴露在四格里，比暴露在手册第 20 页便宜。

### 第一天的活：只做第 0 步

把原始文件复制进 `data/raw/<批次名>/` 并设只读，然后发 **C0-A ＋ C0-B**（写数据台账、建批次目录）。十步里的第 0 步，做完就停。

想知道现在到哪了，不用读文档：

```sh
python3 .etl-utils/check.py --status
```

输出会列出台账标记、产物缺件与下一步。若有多个台账，它会要求用 `--ledger` 指定；若已完成行缺产物，它会报 MISSING。**台账里的 ✅ 不自动等于已经验证。**

### 之后每天三分钟

| 什么时候 | 做什么 |
| --- | --- |
| 开工 | 看定制手册台账的"下一步"列，取编号 → 去 `01-通用手册.md` 搜编号、整段复制 |
| AI 交活 | 看它给的四行（当前／做完／断言／下一步），再做验收四件事（抽一条／查回溯件／勾判据／定下一步） |
| 收工 | 改台账三格：状态、产出物、判据 |

**每步做完必须停**——不是靠 AI 自觉，而是靠你一次只发一条指令：发了 C4-A，它做完就没有下一条可做。

## 检查怎么用（v1.11）

```sh
# 只验当前步，成功不等于整份交付验收
python3 .etl-utils/check.py artifacts/b01 --stage 0
# 有多个手册时明确项目和台账，不猜文件
python3 .etl-utils/check.py --status --project-root /path/to/project --ledger 客户-ETL工作手册.md
# 第 3／7 步使用本项目确认的映射与单位契约
python3 .etl-utils/check.py artifacts/b01 --stage 7 --config check_config.json
```

退出码：**0 所选内置检查齐全通过；1 证据冲突；2 缺件／歧义／无法判定**。不加 `--stage` 是巡检，有未执行项返回 2；不能把 1 条 PASS 加 10 条缺件叫做通过。第 6／8／9 步尚无内置断言，必须另做项目检查或人工验收。

`--status` 只显示台账标记并检查产物路径，不能证明判据已勾完或业务效果成立。相对产物路径从项目根解析，批次短路径须由位置参数或 `artifacts/current` 指定；不自动选最新批次。`current` 可为软链接或一行文本，文本中的相对路径从该文本所在目录解析，例如 `b01`。

配置：将 `check-config.example.json` 复制到项目根的 `check_config.json`，由 AI 按已确认契约替换实值。示例中的字段名、空值写法、0.3 阈值和单位都是演示，不是通用标准。`field_checks.raw` 相对项目 `data/raw`，`clean` 相对批次；每列显式指定 source/target、是否 required，以及有依据时的 max_drop（0～1）。没有 max_drop 时只展示非空率，不作下降判定；本检查不能证明记录身份或每个值都正确。

`unit_checks` 声明指标 id、值字段、单位字段及预期单位。若要核对展示换算，再声明 display、display_unit、expected_display_unit、scale（展示值＝原值÷scale，精确比较；需要舍入的项目应另写规则）。指标文件支持 `metrics` 列表、顶层列表或 id→对象；其他查询结果结构需要项目适配，脚本会返回未完成验证。没有契约时不会据任意两个数字的比值判单位错误。

YAML 检查需要 `PyYAML`；未安装会明确报 MISSING。`--selftest` 同时运行文件检查和 `test_check.py` 中的合成正反例回归；测试不读取客户数据。

## 两条主线的分工（别搞混）

- **通用手册＝怎么做**：方法论、指令全文、验收话术，跨客户不变；
- **定制版手册＝这一单做什么**：只写实值（表名／字段／枚举／时间窗）、本单特有的坑、进度台账。**方法论只引编号，不复制正文**——所以它通常在 300 行左右，超过 600 行基本就是在抄书。

**日常干活是这两份配合着用，三步**：打开定制手册第 N 步 → 看到"发 C3-A ＋ C3-A2" → 去通用手册搜这个编号、整段复制发给 AI。所以**旧手册不会作废，它永远是唯一的指令来源**；定制手册只负责告诉你"发哪条、这单要小心什么"。

## 六条设计原则

上面「理念」讲的是 *ETL 这件事该信什么*（why）；这里六条讲的是 *这套工具怎么把它落成规矩*（how）。

1. **只写差异**：定制版不复制方法论，否则文件越长越没人看；
2. **证据优先**：每条结论带出处，指不出出处的降级为"推断"或"待核"；
3. **契约先读**：动手前先读 schema 的枚举与必填、导入器的硬校验、计数口径、字段类型——这一条能省掉半天返工；
4. **✅ 的门槛是硬的（三样）**：产出物真实存在 ＋ 判据勾完 ＋ **该步的回溯件已生成**。不接受"已完成"这类口头结论；
5. **能验也要能追**：验收时除了问"这个数对不对"，还要问"三个月后还解释得了吗"——批次目录、版本号、隔离原文三样缺一，数就成了没法解释的数；
6. **不绑定项目细节**：不假设字段名、文件名、规模、角色——每条规则都要能换个客户照样成立；做不到就写成"提示"，不写成"失败"。

## 适合谁

- 用 AI 做数据整理、但苦于"审不出来对不对"的人；
- 需要在多个客户/项目间复用同一套流程的人；
- 想把"数据能支持什么结论、不能支持什么"写清楚、而不是只交数字的人。

**不适合**：纯写 SQL 的数仓开发（这套侧重"从原始导出到可信结论"的全流程，不涉及建模调优）；也不适合想要开箱即用工具链的人——它是一套**工作方法 + 指令模板**，附带范围有限的检查脚本。
