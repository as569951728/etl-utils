# etl-utils

> **第一次用 / 隔了很久回来？先看 [START-HERE.md](START-HERE.md)** —— 它只回答一个问题：你现在该干什么。
> 想先弄懂这是什么，再往下读。

> **把"客户给的一堆导出"变成"能入库、能对账、别人敢拿去作决定的结论"——一套可以直接交给 AI 执行的 ETL 工作手册。**
>
> 十步流程 · 11 条可复制指令 · 4 件通用工具 · 附「生成定制版手册」的话术与进度台账

写这套东西的起因很具体：让 AI 写 ETL 代码，它半小时代码就写完了，但你**验证不了对不对**——它说"缺失值已处理"，你只能信。这个仓库解决的就是这一段：**把"怎么验收"写进流程，而不是事后补**。

## 它解决三个具体问题

| 问题 | 这套东西怎么处理 |
| --- | --- |
| AI 交回来的东西没法验 | 每条指令末尾强制"数／位／法"：条数、文件行号或可重跑的查询、一行能复算的公式。指不出来的，等于没做 |
| 换个客户，之前的方法用不上 | 通用手册管"怎么做"，另有一份话术让 AI 按新业务生成"定制版"，只写这一单的实值与坑 |
| 做到一半忘了自己在哪 | 十行进度台账：状态四态（⬜🟡✅⛔）＋ 每步可勾选的过关判据，✅ 只认"产出物存在＋判据勾完" |

## 快速开始

```sh
# 1) 在你的项目里拉一份
cd /path/to/your-project
git clone https://github.com/as569951728/etl-utils.git .etl-utils

# 2) 项目根的 AGENTS.md（没有就新建）加一行
#    ETL 工具包在 .etl-utils/，按它的 README 与 AGENTS.md 执行；出定制手册前先读 03。

# 3) 对 AI 说
#    "读 .etl-utils，给这个客户出一份 ETL 手册"
```

它会先起草**四格背景**（客户与目标／数据清单／已发现问题／已问过谁）等你确认——四格错了整份手册全错，所以这一步单独走一轮。

## 两条主线的分工（别搞混）

- **通用手册＝怎么做**：方法论、指令全文、验收话术，跨客户不变；
- **定制版手册＝这一单做什么**：只写实值（表名／字段／枚举／时间窗）、本单特有的坑、进度台账。**方法论只引编号，不复制正文**——所以它通常在 300 行左右，超过 600 行基本就是在抄书。

**日常干活是这两份配合着用，三步**：打开定制手册第 N 步 → 看到"发 C3-A ＋ C3-A2" → 去通用手册搜这个编号、整段复制发给 AI。所以**旧手册不会作废，它永远是唯一的指令来源**；定制手册只负责告诉你"发哪条、这单要小心什么"。

## 六条设计原则

1. **只写差异**：定制版不复制方法论，否则文件越长越没人看；
2. **证据优先**：每条结论带出处，指不出出处的降级为"推断"或"待核"；
3. **契约先读**：动手前先读 schema 的枚举与必填、导入器的硬校验、计数口径、字段类型——这一条能省掉半天返工；
4. **✅ 的门槛是硬的（三样）**：产出物真实存在 ＋ 判据勾完 ＋ **该步的回溯件已生成**。不接受"已完成"这类口头结论；
5. **能验也要能追**：验收时除了问"这个数对不对"，还要问"三个月后还解释得了吗"——批次目录、版本号、隔离原文三样缺一，数就成了没法解释的数。
6. **不绑定项目细节**：不假设字段名、文件名、规模、角色——每条规则都要能换个客户照样成立；做不到就写成"提示"，不写成"失败"。

## 适合谁

- 用 AI 做数据整理、但苦于"审不出来对不对"的人；
- 需要在多个客户/项目间复用同一套流程的人；
- 想把"数据能支持什么结论、不能支持什么"写清楚、而不是只交数字的人。

**不适合**：纯写 SQL 的数仓开发（这套侧重"从原始导出到可信结论"的全流程，不涉及建模调优）；也不适合想要开箱即用工具链的人——它是一套**工作方法 + 指令模板**，不是一个框架。
